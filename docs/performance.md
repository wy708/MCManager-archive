# 性能与数据边界

## 已有控制

- 采集器以后台线程处理磁盘队列、批量上传和重试，平台按稳定编号幂等处理。
- 高频状态合并、限额与补传和正常事件分离，避免为每个指标单独发请求。
- 页面分包，首页不获取三维几何；低于首屏的图表接近可见区域才初始化。
- 世界故事图表共享限定日期的查询结果，切换图表不重新扫描整个事件库。
- 首页运行摘要只读选定的一台服务器，不自动轮询所有档案。
- 场景转换有并发/队列上限和超时，同一工程共用任务与缓存。
- 三维预览先按施工起点或浏览器记忆的高度读取；选择全部高度才扩大读取。
- `/ai` 有玩家冷却、全服速率和等待数量上限，普通聊天不会调用模型。

## 仍有成本的操作

大型区域的初次扫描、地图补绘、完整高度的复杂场景、GLB 导出和大量历史补传会消耗 CPU、内存、磁盘及带宽。减少浏览器数据量不等于减少所有服务器转换工作。活动实体和复杂资源会增加模型体积。

请求次数不能单独代表负载：应同时检查路径分布、响应大小、错误/重试、队列积压、CPU、磁盘延迟和数据库查询。反向代理计数可能还包含瓦片、静态资源和健康检查。

## 建议观测

先用代表性的玩家数与工程大小建立基线，再逐步提高扫描范围和保留期。对照整机与进程指标，保留采集时间与缺口。尚未提供通用的「可承载多少玩家」基准，不能把隔离测试当作大型服务器压力测试。

游戏进程退出后，原生采集器不再继续采样整机。如果需要停服期间的独立主机监控，应另外部署主机监控服务。
